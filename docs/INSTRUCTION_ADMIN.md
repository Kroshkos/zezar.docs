# Инструкция для роли «Администратор» (ADMIN)

Пошаговое руководство администратора системы «ЦЕЗАРЬ»: учётные записи, пароли,
подразделения, глобальные справочники, уведомления и рассылки, аудит, безопасность
и первые шаги после установки. Описано каждое действие: куда нажать, что выбрать,
что произойдёт.

**Кто такой «Администратор»?** Владелец системы: создаёт пользователей и
подразделения, раздаёт глобальные роли, сбрасывает пароли, настраивает Telegram-бота
и Яндекс-синхронизацию, видит сквозной аудит. Всё, что касается **учётных записей
и сервера** — здесь.

## 1. Как стать администратором и войти

### 1.1. Единственный контур входа

Вход в систему — **только логин + пароль** на странице `/login`. Авторизация через
сторонние сервисы (Яндекс ID/OAuth) удалена полностью; регистраций, приглашений по
e-mail и ссылкам нет. Доступ получает только тот, кого создал администратор.

![Экран входа](IMAGE_PLACEHOLDER_login.png)

### 1.2. Env-администратор (главный, «аварийный ключ»)

Первый администратор задаётся переменными окружения при развёртывании:

* `ADMIN_USERNAME` (по умолчанию `admin`) и `ADMIN_PASSWORD`;
* при каждом старте сервиса сид **синхронизирует** эту учётку: нет пользователя —
  создаёт с ролью ADMIN; есть, но роль сбилась — восстанавливает ADMIN
  (защита от случайного понижения через API);
* несколько env-админов: `ADMIN_LOGINS=user1:pass1,user2:pass2`.

Вход env-админа — обычный: страница `/login`, логин и пароль из `.env`.

> ⚠️ В списке пользователей env-аккаунт помечен особо и защищён от понижения роли.
> Если вы единственный админ — система не даст вам убрать себе права.

### 1.3. Другие администраторы

Создаются действующим админом: обычный пользователь + смена глобальной роли на
«Администратор» (разделы 4.1 и 6).

## 2. Первые шаги после установки — чек-лист

Выполняйте по порядку, отмечая галочки:

1. ☐ Войдите под env-админом (`ADMIN_USERNAME`/`ADMIN_PASSWORD`).
2. ☐ Смените пароль env-админа на стойкий (аватар → «Смена пароля»; либо сразу
   задайте надёжный в `.env` до первого старта).
3. ☐ Создайте подразделения (раздел 5.1). Базовые модули подключатся автоматически.
4. ☐ Создайте пользователей: участников, руководителей, координаторов; выдайте
   начальные пароли (раздел 4.1).
5. ☐ Назначьте руководителям роли HEAD в их пространствах (раздел 5.3).
6. ☐ Настройте глобальные справочники под регламент (раздел 7).
7. ☐ При необходимости: Telegram-бот и сценарии уведомлений (разделы 9–10).
8. ☐ Проведите тестовые действия (вход под демо-пользователем, создание задачи) и
   проверьте журнал событий (раздел 8).

## 3. Страница «Администрирование» (`/admin`)

Открывается из сайдбара. Секции:

1. **Пользователи** — список, поиск, создание, роли, пароли (раздел 4);
2. **Подразделения** — рабочие пространства (раздел 5);
3. **Глобальные справочники** — шаблоны статусов/приоритетов/типов (раздел 7);
4. **Уведомления** — сценарии и рассылки (раздел 9);
5. **Журнал событий** — системный аудит (`/admin/events`, раздел 8).

Пространство для администрирования состава/модулей выбирается селектором справа
вверху; открыть можно без параметров — система сама выберет пространство.

![Страница /admin: секции Пользователи / Подразделения / Справочники / Уведомления](IMAGE_PLACEHOLDER_admin_main.png)

## 4. Пользователи — все операции по шагам

### 4.1. Создать пользователя

1. `/admin` → «Пользователи» → кнопка **«+»**.
2. Заполните:
   * **Фамилия Имя** (как в кадровых документах — так вас найдут руководители при
     добавлении в состав);
   * **Логин** — короткий, без пробелов (принятая схема: `ivanovii`);
   * **E-mail** — необязательно;
   * **Начальный пароль** — придумайте и передайте человеку по защищённому каналу;
   * **Глобальная роль**: Участник / Руководитель / Координатор / Администратор.
3. Сохраните.
4. При первом входе пользователь **обязан сменить пароль** (флаг `must_change_password`
   включается автоматически, в т.ч. после любого вашего сброса).

![Форма создания пользователя](IMAGE_PLACEHOLDER_admin_user_create.png)

### 4.2. Найти пользователя

Поле поиска — по имени/логину; фильтр — по подразделению.

### 4.3. Редактировать

Строка пользователя → «Редактировать»: ФИО, e-mail, глобальная роль, активность.
* **Блокировка**: снимите признак активности — вход мгновенно запрещён
  («Учётная запись заблокирована»), данные и карточки сохраняются.
* Разблокировка — обратное переключение.

### 4.4. Сбросить пароль (сотрудник забыл)

1. Найдите пользователя → **«Сброс пароля»**.
2. Задайте новый начальный пароль → сохраните.
3. Сообщите пользователю; при следующем входе система снова потребует обязательную
   смену пароля.

### 4.5. Удалить учётную запись

Строка пользователя → удаление (с подтверждением). Что происходит:

* учётка и членства удаляются;
* **карточки, где человек был ответственным, НЕ удаляются** — они останутся с
  «висящим» ответственным. Правильный порядок: сначала переназначьте ответственных
  во всех его карточках (фильтр по ответственному в нужных пространствах), потом удаляйте.

## 5. Подразделения (рабочие пространства)

### 5.1. Создать подразделение

1. `/admin` → «Подразделения» → **«+»** → название → сохранить.
2. Автоматически создаётся рабочее пространство с **базовыми модулями**:
   Дашборд, Задачи, Проекты, Совещания, Администрирование. Отключить их нельзя.

### 5.2. Переименовать / деактивировать

Строка подразделения → «Редактировать» (название) или деактивация (скрывает
пространство из активной жизни; данные сохраняются — это безопаснее удаления).

### 5.3. Состав и роли HEAD/MEMBER

1. Выберите пространство селектором → вкладка **«Состав»**.
2. «+» → поиск по фамилии/логину среди всех пользователей → роль
   **Участник (MEMBER)** или **Руководитель (HEAD)**.
3. Смена роли — в выпадающем списке строки состава; применяется **мгновенно**
   (сессия пользователя перевыпускается с новыми правами, перелогин не нужен).

Инварианты системы (не обходятся никак):

* в пространстве всегда **≥1 руководитель**: понижение или исключение последнего
  HEAD отклоняется с HTTP 409 и понятным текстом. Порядок замены: сначала
  назначьте нового HEAD, потом понижайте старого;
* повышение до HEAD доступно глобальным акторам (вам/координатору) и штатно
  выполняется со страницы состава.

![Вкладка «Состав» пространства](IMAGE_PLACEHOLDER_add_member.png)

## 6. Глобальные роли: как они связаны с пространствами

| Глобальная роль | Даёт |
|---|---|
| Участник (MEMBER) | Работа в карточках своих пространств |
| Руководитель (HEAD) | Синхронизируется с ролью HEAD в пространстве: назначение руководителем автоматически повышает глобальную роль, снятие — понижает (если человек больше нигде не HEAD) |
| Координатор (COORDINATOR) | Все пространства, кадры, справочники, шеринги (см. «Инструкция — Координатор») |
| Администратор (ADMIN) | Полная админка этой инструкции |

Смена глобальной роли: `/admin` → пользователь → «Роль». Права применяются сразу;
при жалобах «права не обновились» сверяйте время события смены роли с действиями
пользователя в журнале (раздел 8) и убедитесь, что работает один экземпляр сервиса
(раздел 13).

## 7. Глобальные справочники

Статусы, приоритеты, типы сущностей, маршруты рабочих процессов, группы задач —
**глобальные шаблоны** (`department_id = NULL`). Их видно всем пространствам, где
включён соответствующий модуль; руководители активируют копии у себя.

Как вести:

1. `/admin` → «Глобальные справочники» → выберите вид (статусы задач и т.п.).
2. «+» — новая запись (название, цвет, порядок); редактирование — клик по строке.
3. Деактивация скрывает шаблон из предложения новых копий (уже активированные
   копии в пространствах не ломаются).

> ⚠️ Правки глобального шаблона влияют на **все** пространства. Меняйте осознанно,
> о крупных изменениях объявляйте заранее (например, массовой рассылкой — раздел 9.2).

![Глобальные справочники](IMAGE_PLACEHOLDER_refdata_global.png)

## 8. Журнал событий (системный аудит) `/admin/events`

Что пишется: входы/выходы, неудачные попытки и блокировки IP, CRUD карточек,
кадровые решения (добавление/исключение/смена ролей), шеринги, рассылки,
системные события.

Как пользоваться:

1. Откройте `/admin/events`.
2. Фильтр по категории (Auth / Users / Entities / Sharing / System…) + поиск по тексту.
3. Клик по событию — подробности (кто, откуда, что изменил, было→стало).

Типовой разбор жалобы «мне поменяли роль, а права не обновились»:
найдите событие смены роли → сравните его время с последующими действиями
пользователя → если действия шли «по старым правам» дольше секунды — проверяйте
число экземпляров сервиса (раздел 13).

![Журнал событий с фильтрами](IMAGE_PLACEHOLDER_admin_events.png)

## 9. Уведомления и рассылки

### 9.1. Сценарии уведомлений

`/admin` → «Уведомления» → «Сценарии»:

* **базовые сценарии** — системные, неотключаемые (событие → кому → шаблон сообщения);
* **пользовательские сценарии** — можно создавать: выберите событие, audience
  (кому: ответственный, руководитель пространства, всё пространство, роль…),
  шаблон текста; тумблер вкл/выкл; редактирование в любой момент;
* кнопка **«Тест»** — отправить сообщение себе, чтобы проверить шаблон и доставку.

### 9.2. Массовая рассылка (broadcast)

Для объявлений («изменение регламента статусов», «профилактика»):

1. «Уведомления» → «Массовая рассылка».
2. Текст сообщения.
3. Аудитория: **все** / по подразделениям / по глобальным ролям.
4. **«Предпросмотр получателей»** — обязательно посмотрите список перед отправкой.
5. Отправить сразу или **запланировать** на дату/время. Planned можно отменить.
6. Очередь фактической отправки видна в **outbox**; статус воркера — в разделе статуса.

![Форма массовой рассылки с предпросмотром](IMAGE_PLACEHOLDER_broadcast.png)

## 10. Telegram-бот — настройка администратора

1. Зарегистрируйте бота у @BotFather, получите токен.
2. Положите токен в переменную окружения `TELEGRAM_BOT_TOKEN` (в `.env` / параметрах
   хостинга) и перезапустите сервис. Без токена система работает, рассылка просто
   выключена.
3. Long-polling-воркер бота запускается внутри приложения; его статус виден в
   разделе статуса уведомлений.
4. Пользователи привязываются **сами**: бот запрашивает логин и пароль ЦЕЗАРЬ,
   затем сам удаляет эти сообщения из диалога (пошагово — «Инструкция — Участник»,
   раздел 14). Коды доступа не используются; неизвестный логин бот молча игнорирует.
5. Команды пользователей: `/mute`, `/unmute`, `/help`.

Проверка настройки: отправьте тест по своей учётке (9.1 «Тест») — сообщение должно
доехать. Не доехало: чат с ботом не привязан? воркер запущен? аутрич-трафик к
`api.telegram.org` не блокируется?

## 11. Яндекс Календарь — ваша зона

Синхронизацией карточек в личные календари занимается **фоновый воркер** с периодом
`SYNC_INTERVAL_SECONDS` (по умолчанию 300 секунд). Пользователи вводят свои логины
Яндекса и пароли приложения самостоятельно на странице «Интеграции» — вы их пароли
не видите (хранятся Fernet-шифром) и **не должны** пытаться получить.

Ваша работа:

* ошибки конкретного пользователя (отозванный пароль приложения → 401/403) **не
  влияют** на остальных; помогите человеку переподключиться: пусть создаст новый
  пароль приложения на `id.yandex.ru/security/app-passwords` (сервис «Другие») и
  заново сохранит на «Интеграциях»;
* сетевые требования: исходящий доступ к `webdav.yandex.ru` (старый `dav.yandex.ru`
  не поддерживается);
* параметры `YANDEX_CAL_*` — при необходимости переопределения пути/имени календаря.

## 12. Безопасность — что система делает за вас и что должны вы

Механизмы системы:

* пароли хранятся только хешами (bcrypt-style); начальный пароль ставите вы;
  обязательная смена при первом входе;
* **защита от перебора**: ≤10 неудачных попыток с одного IP за 15 минут → временная
  блокировка IP (событие в журнал);
* сессионная cookie: 14 дней, HttpOnly, SameSite=Lax, Secure в production;
  подпись HMAC-SHA256;
* app-пароли Яндекса — только Fernet-шифротекст в БД;
* CSP/X-Frame-Options/nosniff выдаются middleware;
* **fail-fast**: в production приложение **не стартует**, если `SECRET_KEY` остался
  `change-me` или короче 32 символов, включён dev-режим/dev-логин/демо-сид, или не
  заданы `ADMIN_USERNAME`/`ADMIN_PASSWORD`.

Ваши обязанности:

1. Длинный случайный `SECRET_KEY` (≥32 символов), не менять местами между срезами.
2. HTTPS обязателен (за TLS — reverse-proxy; см. DEPLOY.md).
3. Не передавать начальные пароли по открытым каналам; требовать их смены.
4. Регулярно (ежедневно) проверять бэкап БД (`VACUUM INTO` снапшота `/data/caesar.db`).
5. Раз в квартал — ревизия списка админов и активных пользователей.
6. Блокировать (деактивировать) учётки уволенных в день увольнения.

## 13. Ключевое эксплуатационное ограничение: ОДИН экземпляр

SQLite + in-process воркеры (Telegram long-polling, outbox, календарный воркер,
кэш прав `acl_epoch`) рассчитаны ровно на **один процесс** сервиса:

* несколько копий с общей БД дадут `database is locked` и рассинхрон кэша прав
  («роль поменяли, а интерфейс старый»);
* следите, что хостинг/оркестратор не поднимает второй контейнер с тем же `/data`;
* план роста при >~50 активных пользователей — PostgreSQL + внешний воркер
  (обсуждается с техспециалистами, см. «Инструкция — Технические специалисты»).

## 14. Диагностика типовых проблем

| Симптом | Причина / действие |
|---|---|
| Жалоба «нельзя создать карточку в своём пространстве» | Проверьте членство в пространстве (вкладка «Состав»). Ложные срабатывания исправлены в актуальной версии (membership проверяется раньше глобальной роли) — обновите сервис |
| После смены роли у пользователя «старое» отображение | Права применяются мгновенно (cookie перевыпускается с новым epoch). Наблюдается стабильно → проверьте ровно один экземпляр на одной БД |
| Не удаётся понизить последнего руководителя | Штатный инвариант: сначала назначьте второго HEAD |
| Контейнер падает на старте | Fail-fast (раздел 12): SECRET_KEY, ADMIN_USERNAME/PASSWORD, DEV-флаги |
| «database is locked» | Два процесса пишут в одну SQLite — оставьте один экземпляр |
| Cookie слетает, постоянные выходы | Нет HTTPS / не проброшен `X-Forwarded-Proto` на прокси |
| Пользователь забыл пароль | Раздел 4.4 «Сброс пароля» |
| Рассылка «зависла» | Посмотрите outbox и статус воркера (раздел 9.2); проверьте токен бота (раздел 10) |
| У одного пользователя календарь встал | Отозван пароль приложения (401/403) — переподключение на «Интеграциях» (раздел 11) |

Более глубокая техническая диагностика — в «Инструкции — Технические специалисты»
и `DEPLOY.md`.
